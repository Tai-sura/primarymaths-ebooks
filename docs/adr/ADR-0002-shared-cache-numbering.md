# ADR-0002 — 兩個站的 CACHE 號碼共用一組，一號一內容

狀態：已接受 · 2026-11-27 · 相關：`REPO.md`（兩個 repo 各一份）、`docs/01-workflow.md` Stage 7

## 背景

`physics-ebooks` 與 `primarymaths-ebooks` 各自在自己的 `sw.js` 裡有一個 `CACHE = "ebooks-v<N>"`。兩個站是獨立的 GitHub Pages，service worker 也各自註冊。

如果兩個站各自由 v1 數起，會出現兩種號碼相同但內容不同的情況。已經發生過一次：一批改動預定用 v158，但另一條線先把 v158 用掉（jpwm01 的答案卡拖曳），令兩個不同內容同號。

## 決定

1. **一個號碼只代表一次內容發佈**，兩個站共用同一組遞增編號。
2. 上線前先 `git fetch`，看 `origin/main:sw.js` 的現值（以及另一站的現值），取較大者 +1。預定號被別條線用掉就**順延**到下一個空號，不得同號兩內容。
3. 號碼只由 Chief 改；其他 Bot 不改 `sw.js`、不 bump CACHE。
4. 推完要驗：線上 `sw.js` 的 `ebooks-v<N>`、`caches.keys()` 只剩該號。

## 被否決的選擇

| 方案 | 為什麼不做 |
|---|---|
| 兩站各自編號 | 同號不同內容，除錯時無法憑號碼判斷新舊 |
| 用時間戳做版本 | 快取比對變成字串比較，看不出先後，也難在 commit 訊息引用 |
| 用內容 hash | 每次建置都變，無法「這批是第幾版」溝通 |

## 後果

- 好處：任何一個號碼在全團隊只有一個意思；使用者報告問題時講型號就夠。
- 代價：兩站要協調；一邊跳號另一邊會見到「中間有幾個號沒用過」，這是正常的。

## 何時重看

- 站數超過兩個。
- 引入需要獨立版本節奏的部署（例如 app 與內容分開發佈）。
